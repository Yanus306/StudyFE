## STUDYFE
### 🚀 프론트엔드 개인 프로젝트 스터디

프론트엔드(Front-End) 스터디 레포지토리입니다. 개별 폴더에서 각자의 프로젝트를 진행하며, PR을 통해 서로의 코드를 리뷰하고 함께 성장합니다.

---

#### 📂 폴더 구조

이 레포지토리는 스터디원 각자의 독립된 작업 공간으로 나뉘어 있습니다.

```text
.
├── 📁 Doyun/        # 도윤
├── 📁 Hoseong/      # 호성
├── 📁 Minju/        # 민주
├── 📁 Minseong/     # 민성
└── 📁 Seungjun/     # 승준
```

## 🛠 스터디 규칙 및 프로세스

### 1. 브랜치 전략 및 생성 규칙
* `main` 브랜치는 최종 작업물만 모이는 공간입니다. **절대 `main` 브랜치로 직접 push하지 마세요!**
* 새로운 작업을 시작할 때는 항상 `main` 브랜치에서 최신 코드를 `pull` 받은 후, 본인의 개인 브랜치를 생성하여 진행합니다.
* **브랜치명 생성 규칙:** `[타입]/[본인이름]-[작업내용]` (모두 소문자로 작성하는 것을 권장합니다.)
  * 예시: `feat/minju` (민주의 기능 추가 브랜치)
  * 예시: `fix/minju` (민주의 버그 수정 브랜치)
  * 예시: `docs/minju` (민주의 문서 수정 브랜치)

### 2. 작업 및 PR 프로세스
1. `main` 브랜치에서 본인의 작업 브랜치를 생성합니다. (`git checkout -b feat/minju-login`)
2. 본인 폴더 내에서 열심히 개발을 진행하고 커밋합니다.
3. 작업 완료 후 원격 저장소에 push하고, `main` 브랜치를 향해 **PR(Pull Request)**을 생성합니다.
4. **최소 1명 이상의 스터디원에게 리뷰와 승인(Approve)**을 받은 후 `main` 브랜치에 최종 merge 합니다.

## 💬 커밋 메시지 규칙 (Commit Message Convention)

일관된 커밋 히스토리를 위해 아래 규칙을 준수합니다. 커밋 메시지 서두에 본인의 이름을 붙여 가독성을 높입니다.

> **구조:** `[타입]: [이름] - [작업 내용]`  
> **예시:** `feat: 민주 - 리스트 컴포넌트 추가`

| 타입 (Type) | 설명 |
| :--- | :--- |
| `feat` | 새로운 기능 추가 |
| `fix` | 버그 수정 |
| `docs` | 문서 수정 (README, 주석 등) |
| `style` | 코드 포맷팅, 세미콜론 누락 등 (코드 자체의 변경이 없는 경우) |
| `refactor` | 코드 리팩토링 (기능 추가나 버그 수정이 없는 구조 개선) |
| `test` | 테스트 코드 추가 및 수정 |
| `chore` | 패키지 매니저 설정, 빌드 업무 등 (자잘한 수정) |
